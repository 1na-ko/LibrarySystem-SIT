## 二、严重问题（P0 — 必须立即修复）

### P0-1 🔴 GraphQueryServiceImpl 图谱路径解析完全失效

**文件**: `library-knowledge-graph/src/main/java/com/library/kg/service/impl/GraphQueryServiceImpl.java`  
**方法**: `buildGraphFromPaths()` (第 103-149 行)  
**影响**: `GET /kg/book/{bookId}/graph` 端点始终返回空节点/边——图谱可视化功能完全不可用。

**根因**: 方法尝试将 Neo4j Driver 的路径结果解析为包含 `_nodes` / `_relationships` 键的 Map，但 Neo4j 5.x Driver 的 `Value.asList()` 在 path 类型上返回交替的 `Node` / `Relationship` 值列表，不含这两个键。`segVal.asMap()` 调用永远找不到 `_nodes` / `_relationships`，异常被静默捕获并记录为 DEBUG 日志。

**修复方向**: 按 Neo4j Driver 5.x API 正确解析 path segment——通过 `Value.type().name()` 区分 NODE / RELATIONSHIP，从 `Node.asMap()` 提取业务属性，从 `Relationship` 提取 `startNodeElementId()` / `endNodeElementId()` 和 `type()`。

### P0-2 🔴 GraphQueryServiceImpl 边 ID 解析将导致 NumberFormatException

**文件**: 同上，`buildEdgeFromValue()` 方法 (第 184-189 行)  
**代码**:
```java
Long.parseLong(relVal.asRelationship().startNodeElementId())
```
**影响**: 运行时 `NumberFormatException`——图谱所有边构建失败。

**根因**: Neo4j 5.x 的 element ID 格式为 `"4:abc123def:0"`（字符串），不可被 `Long.parseLong()` 解析。回退使用的 `startNodeId()` 返回 Neo4j 内部本地 ID，与业务 `GraphNode.id` 不匹配，导致前端边连接指向错误节点。

**修复方向**: 使用字符串形式的 elementId 作为图的 identity，或在构建节点时统一使用 Neo4j 内部 ID 并在 GraphNode 中存储该值。

## 三、高优先级问题（P1 — 本迭代修复）

### P1-1 🟠 BookAdminServiceImpl.updateBook() 修改 totalCopies 时未调整 availCopies

**文件**: `library-core/src/main/java/com/library/core/service/impl/BookAdminServiceImpl.java` (第 91-93 行)  
**影响**: 增加总册数时新增册数不可借（availCopies 未同步增加）；减少总册数时可能出现 `availCopies > totalCopies` 的不合理状态。

**修复方向**:
```java
if (dto.getTotalCopies() != null) {
    int delta = dto.getTotalCopies() - book.getTotalCopies();
    book.setTotalCopies(dto.getTotalCopies());
    book.setAvailCopies(Math.max(0, book.getAvailCopies() + delta));
}
```

### P1-2 🟠 ReservationServiceImpl.reserve() 存在 TOCTOU 竞态条件

**文件**: `library-core/src/main/java/com/library/core/service/impl/ReservationServiceImpl.java` (第 70-78 行)  
**影响**: 并发请求下同一用户可能对同一本书创建多条 WAITING 状态预约——`selectCount → insert` 之间无原子性保证。数据库表 `reservation` 缺少 `UNIQUE (user_id, book_id, status)` 约束。

**修复方向**: 添加数据库唯一约束（需 Flyway 迁移 V6），或在 Java 层加 Redis 分布式锁。

### P1-3 🟠 TopicNetworkBuilderImpl Jaccard 相似度 Cypher 有缺陷

**文件**: `library-knowledge-graph/src/main/java/com/library/kg/service/impl/TopicNetworkBuilderImpl.java` (第 125-136 行)  
**代码**: `COUNT(DISTINCT k1) AS freq1`  
**影响**: `MATCH (k1)<-[:HAS_KEYWORD]-(:Book)` 中 `k1` 已绑定到特定关键词，`COUNT(DISTINCT k1)` 恒为 1。所有 `RELATED_TO` 边权重计算错误。

**修复方向**: 将 `COUNT(DISTINCT k1)` 改为 `COUNT(DISTINCT b)`（统计与关键词关联的图书数）。

### P1-4 🟠 EmbeddingServiceImpl 缺少重试逻辑和网络异常包装

**文件**: `library-ai/src/main/java/com/library/ai/embedding/EmbeddingServiceImpl.java`  
**影响**: 与 `LlmServiceImpl` 的不一致——Embedding API 调用无 `retryWhen` 重试、无 `onErrorMap(IOException.class)` 包装。DashScope API 瞬时故障或网络抖动直接抛出原始 `IOException`，绕过 `AiExceptionHandler`，最终作为 HTTP 500 返回。

**修复方向**: 参考 `LlmServiceImpl.executeWithRetry()` 模式，为 `doEmbed()` 添加指数退避重试和网络异常包装。

## 九、架构落地评估

| 架构原则 | 评估 | 说明 |
|----------|------|------|
| Modular Monolith 边界 | ✅ 合规 | 模块按领域边界划分，依赖方向严格单向 |
| SPI 端口模式 | ✅ 优秀 | `core` 定义接口 → `kg` 实现 → `ObjectProvider` 消费，依赖反转标准范式 |
| 领域事件通信 | ✅ 合规 | 所有跨模块通知通过 Spring Events，`AFTER_COMMIT` 保证事务一致性 |
| Controller 落位 ADR | ✅ 合规 | 鉴权上下文 Controller 在 security，只读 Controller 在 core/kg/acquisition |
| 分层架构 | ⚠️ 轻微偏离 | `BookController.getDetail()` 在 Controller 层修改 VO——应下沉至 Service |
| 全局逻辑删除 | ✅ 合规 | 全局 `logic-delete-field: deleted` + V1 全部 10 表统一 `deleted` 列 |
| ES 最终一致性 | ✅ 合规 | MySQL 主存储，事件异步同步 ES，`AFTER_COMMIT` + 指数退避重试 |
| LLM 降级策略 | ✅ 合规 | 所有 LLM 调用点含 try-catch + 模板/规则降级路径 |

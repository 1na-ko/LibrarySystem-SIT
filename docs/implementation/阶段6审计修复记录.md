## 2. P0 阻断级修复

### 2.1 ES 按分类筛选功能缺陷修复

**问题**：`BookDocument` 无 `categoryId` 字段，`EsIndexInitializer` mapping 未声明，`ESSyncListener.buildDocument` 未写入；但 `BookESRepository` 三处（全文搜索 / 高级搜索 / 热门图书）对 `categoryId` 做 term 查询。ES 中字段不存在时 term filter 静默匹配空集 → **按分类搜索/热门榜筛选永远返回空**。这是阶段 3 已交付的功能性缺陷。

**修复**：
- `BookDocument` 新增 `categoryId`（+ `coverUrl` / `location`）字段
- `EsIndexInitializer.createIndex` mapping 增 `categoryId`(long) / `coverUrl`(keyword) / `location`(keyword)
- `ESSyncListener.buildDocument` 同步写入三字段

> **部署提示**：`EsIndexInitializer` 幂等（索引已存在则跳过）。已有 ES 索引需删除重建以生效新 mapping：`curl -X DELETE localhost:9200/books` 后重启服务自动重建。

### 2.2 AdminBookController 分层合规

**问题**：`AdminBookController` 直接注入 `BookMapper` / `BorrowRecordMapper` 并在方法体内调用，违反 CLAUDE.md §6 硬性禁止项①（Controller 直接调 Mapper）。且事件发布游离于事务边界外，`AFTER_COMMIT` 时序保证实际未生效（靠 `fallbackExecution` 兜底为同步执行）。

**修复**：
- 新增 `BookAdminService` 接口 + `BookAdminServiceImpl`（library-core），`@Transactional` 内聚 ISBN 唯一校验、活跃借阅检查、乐观锁判断、领域事件发布
- `AdminBookController` 精简为薄委托（仅参数绑定 + 鉴权 + 调 Service），移除 Mapper 依赖
- 事件发布纳入 `@Transactional` 方法内，`@TransactionalEventListener(AFTER_COMMIT)` 时序保证真正生效

## 3. P1 严重级修复

### 3.1 推荐引擎线程池隔离 + 重复全表扫描消除

**问题**：
- `RecommendationServiceImpl` 三路并行召回用 `CompletableFuture.supplyAsync` 未传 Executor，落入 JDK `ForkJoinPool.commonPool`（JVM 全局共享、为 CPU 密集型设计），与 `AsyncConfig.taskExecutor` 配置脱节；且 import 了 `Executors`/`ExecutorService` 却未用（死代码）
- 单次推荐请求对 `borrow_record` 全表扫描 **4 次**（CF 内 1 + Content 内 1 + `loadBorrowedBookIds` 排除已借 1 + `generateReasons` 取已借标题 1），与"N+1 消除"声明矛盾

**修复**：
- 注入 `@Qualifier("taskExecutor") Executor`，`supplyAsync` 显式传入；清理死代码 import
- `RecommendationServiceImpl.recommend()` 顶层一次性加载 `List<BorrowRecord> allRecords`，派生 `borrowedBookIds`，分发给 CF / Content / 排除逻辑 / 理由生成器复用
- `CollaborativeFilteringService` / `ContentBasedService` 新增接收预加载数据的重载方法（原方法保留委托，供独立测试）
- 全表扫描 **4 → 1 次**
- 并行召回异常 `log.warn` 补传异常对象（保留堆栈）

### 3.2 Redis KEYS → SCAN + 缓存失效接口上提

**问题**：
- `BookSearchServiceImpl.evictAllSearchCache` 用 `redisTemplate.keys()`（O(N) 阻塞主线程，生产禁用），而方法注释却写"通过 Redis SCAN 匹配"——**实现与注释不符**
- `ESSyncListener` 依赖 `BookSearchServiceImpl` 具体类而非 `BookSearchService` 接口（SOLID 依赖倒置违反，因 `evictAllSearchCache` 仅在 Impl 上定义）

**修复**：
- `evictAllSearchCache` 改用 `RedisCallback` + `connection.scan(ScanOptions)`（非阻塞迭代，count=500）
- `evictAllSearchCache` 上提至 `BookSearchService` 接口；`ESSyncListener` 改依赖接口

## 7. 借书锁事务边界修复（原技术债，已解决）

**问题**：`BorrowServiceImpl.borrow()` 的 `@Transactional` 方法在 `finally` 内释放 Redis 锁，早于 Spring 事务代理提交，存在提交窗口竞态（其他线程可在锁释放后、事务提交前抢锁读到旧库存）。

**修复方案**：改用 `TransactionSynchronizationManager.registerSynchronization` 注册 `AFTER_COMMIT` 回调——
- **事务激活（生产）**：锁在事务提交后释放，完整覆盖提交窗口
- **无事务上下文（纯 Mockito 单测）**：`isSynchronizationActive()` 为 false 时降级为立即释放，保持单测行为不变（不破坏 `@InjectMocks` 测试）
- **异常路径**：catch 块立即释放锁（事务将回滚，无并发竞态）

**测试覆盖**：新增 `BorrowServiceTest.shouldDeferLockReleaseUntilCommitWhenTransactionActive`——手动激活事务同步，验证借书成功后锁不立即释放、已注册回调、模拟 `afterCommit` 后才释放。

**结果**：全量 332 项测试全绿（core 99），锁与事务提交边界正确对齐，**无遗留技术债**。

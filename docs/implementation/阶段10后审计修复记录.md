## 1. 修复清单（已落地）

### P1：阶段 10 事件总线核心实现缺陷

#### 1.1 `ESSyncListener.onBookEvent` evict 顺序与高频清缓存

**问题**：先 `evictAllSearchCache()` 再写 ES。若 ES 临时不可达，重试 3 次（共 ~7s）期间会出现"缓存空 + ES 旧数据"窗口，所有搜索请求穿透到 ES 形成击穿；同时 `book.*` 队列接收所有事件（含借/还），借还高峰期每次都全量 SCAN+DELETE 搜索缓存，缓存命中率塌陷至接近 0。

**修复**（[`ESSyncListener.java`](../../library-server/library-core/src/main/java/com/library/core/event/ESSyncListener.java)）：
- **顺序调整**：先 `syncToEs`/`deleteFromEs` 成功，再 `evictSearchCacheIfStructureChanged`（重试期间缓存仍为旧版本，与 ES 一致，不击穿）。
- **白名单失效**：仅 `RK_BOOK_CREATED/UPDATED/DELETED` 触发 evict；`borrowed/returned` 仅改 `availCopies/borrowCount`，对全文检索结果集无显著影响，不参与缓存失效。

**测试**：补 2 项 `ESSyncListenerTest`（`shouldSyncBookToEsButNotEvictCacheOnBorrowed` / `shouldSyncBookToEsButNotEvictCacheOnReturned`）。

#### 1.2 `ReservationNotifier` 全局 catch 吞噬异常 → DLQ 永远空

**问题**：消费方法整体 `try { ... } catch (Exception e) { log.error(...) }` 将 Redis/DB 临时不可达异常一并吞掉，Spring AMQP `RetryTemplate` 无法识别失败，**3 次重试 + 死信队列兜底**架构承诺彻底失效——`q.library.events.dlq` 永远不会收到消息。

**修复**（[`ReservationNotifier.java`](../../library-server/library-core/src/main/java/com/library/core/event/ReservationNotifier.java)）：
- 移除外层 `try-catch (Exception)`，让 Redis/DB 临时异常自然抛出由 RetryTemplate 接管。
- 业务级异常（`NumberFormatException` 单条数据格式错误）保留 catch + `continue`（跳过该条不重试，符合幂等性）。
- 设置过期标记的 `try-catch` 保留（次要操作，失败仅日志）。

#### 1.3 `EventBusBridge.@TransactionalEventListener` 移除 `fallbackExecution = true`

**问题**：5 个事件桥接均设 `fallbackExecution = true`（无事务上下文也执行）。此前所有发布点都在 `@Transactional` 内，没出问题；但该开关将隐性削弱"事务提交后才发 MQ"的不变量——未来若新增非事务发布点（容易疏漏），事件会在 MySQL 数据持久化前送出，消费者读到脏数据。

**修复**（[`EventBusBridge.java`](../../library-server/library-core/src/main/java/com/library/core/event/EventBusBridge.java)）：
- 移除 `fallbackExecution = true`，恢复默认 `false`（无事务时 Spring 输出 WARN 并丢弃事件，强制要求所有发布点必须在 `@Transactional` 内调用）。
- 类级 Javadoc 显式说明该约定，便于新开发者理解。

### P1：业务正确性缺陷

#### 1.4 `KgRelatedBookQueryService` Cypher 1 跳查询恒返回空

**问题**：原 Cypher `MATCH (b:Book {id: $bookId})-[*1]-(neighbor:Book)` 仅匹配 Book→Book 直接边（仅 CITES 类型）。但 `GraphBuildService.writeToNeo4j` 实际只创建 `HAS_KEYWORD/AUTHORED_BY/BELONGS_TO`（Book → 中间实体），从不构建 CITES 边。**该 Port 实现长期返回空列表**，KG 相关推荐永远走降级（MySQL 同分类/同作者），架构文档承诺的 KG 多跳推荐未真正落地。

**修复**（[`KgRelatedBookQueryService.java`](../../library-server/library-knowledge-graph/src/main/java/com/library/kg/service/recommend/KgRelatedBookQueryService.java)）：
- Cypher 改为 2 跳通过中间实体：
  ```cypher
  MATCH (b:Book {id: $bookId})-[:HAS_KEYWORD|AUTHORED_BY|BELONGS_TO]-()
        -[:HAS_KEYWORD|AUTHORED_BY|BELONGS_TO]-(neighbor:Book)
  ```
- 显式列出关系类型，避免遍历到不预期的关系（如未来引入的 CITES）。
- Javadoc 说明本系统不构建 CITES 边的设计前提。

#### 1.5 `DuplicateCheckResultVO.isDuplicate` Jackson 序列化字段丢失

**问题**：Lombok 为 `boolean isDuplicate` 生成 `isDuplicate()` getter。Jackson POJO 自省默认将 `isXxx()` 映射为 JSON 字段 `xxx`（剥离 `is` 前缀），实际序列化为 `"duplicate": true`。但 OpenAPI 契约（[`docs/api/library-api.yaml:615`](../api/library-api.yaml)）声明字段名为 `isDuplicate`，**前后端契约不一致**——Android 端按 OpenAPI 解析时 `isDuplicate` 永远为 `null`/默认 `false`，重复图书无法被识别拦截。

**修复**（[`DuplicateCheckResultVO.java`](../../library-server/library-acquisition/src/main/java/com/library/acquisition/vo/DuplicateCheckResultVO.java)）：
- 字段加 `@JsonProperty("isDuplicate")` 显式指定 JSON 字段名。
- Javadoc 说明 Lombok + Jackson 默认行为以避免后续开发者误删。

## 2. 已识别但保留的发现（理由说明）

### 2.1 RabbitListenerContainerFactory 未显式声明（P2，保留）

**子代理 4 误判为 P0**。Spring Boot `RabbitAnnotationDrivenConfiguration.simpleRabbitListenerContainerFactoryConfigurer()` 通过 `@Autowired ObjectProvider<MessageConverter>.getIfUnique()` 自动从容器中取唯一 `MessageConverter` Bean。我们注册的 `Jackson2JsonMessageConverter` 实现了 `MessageConverter`，会被自动注入到默认 `SimpleRabbitListenerContainerFactory`。**消费端实际会用 Jackson 转换器**，不存在反序列化失败问题。

显式声明 ContainerFactory 仅为加固（防止未来引入第二个 `MessageConverter` Bean 后 `getIfUnique()` 返回 null 退化），优先级 P2，记入未来演进项。

### 2.2 `OverdueBatchProcessor` `DuplicateKeyException` rollback-only（P2，无实际影响）

**子代理 2 判定为 P1 死循环**。核验后：catch `DuplicateKeyException` 后 `continue`，**异常未抛出方法外**，Spring `TransactionAspectSupport` 的 rollback-only 标记机制基于"方法异常出口"判断，本 catch 后整批事务**正常 commit**，不会触发 `UnexpectedRollbackException`。子代理判断错误，无需修复。

### 2.3 `BorrowServiceImpl` 步骤 5 仅校验 `status=OVERDUE`（P2，待业务侧确认）

**子代理 2 P1**：当前实现依赖 `OverdueCheckJob` 每天凌晨 3:00 扫描标记 OVERDUE，最坏存在 24h 窗口内"`due_date` 已过但 `status` 仍为 BORROWED/RENEWED"的用户继续借书。

修复方案需复合校验 `(status=OVERDUE) OR (due_date < CURRENT_DATE)`，但需要业务侧确认是"超期日当天即拦截"还是"次日凌晨 Job 跑后才生效"。本次审计不擅自变更业务规则，登记为待业务确认项。

### 2.4 `BorrowServiceImpl` 同用户同书 BORROWED 唯一约束（P2，权衡保留）

**子代理 2 P1**：`borrow_record` 无 `(user_id, book_id, status)` 唯一约束；锁 key 仅按 bookId 不含 userId，并发场景下同用户两次请求可能产生 2 条 BORROWED 记录。

修复需新增 V8 迁移 + 锁 key 改造，影响面较大。当前 7 步校验中 step 4 `selectCount(BORROWED/RENEWED)` 在大部分场景能拦截重复借阅，唯有跨毫秒级并发存在窗口。权衡修复成本与现实风险，登记为未来演进项。

### 2.5 RabbitTemplate 未启用 Publisher Confirms（P2，权衡保留）

**子代理 4 P2**：`rabbitTemplate.convertAndSend` 在连接抖动时不抛异常即返回，`EventBusBridge.publish` 的 `try-catch` 无法感知部分丢失场景。

启用 `publisher-confirm-type: correlated` + `ConfirmCallback` 是更稳妥的做法，但当前架构以 `EsRebuildJob` 周级全量重建作为兜底（[`阶段10完成记录 §2.3`](阶段10完成记录.md)），与"轻量、不上 Outbox"的设计权衡一致，登记为未来演进项。

### 2.6 RBAC 测试用例允许 `403` 旁路（P2，登记）

**子代理 4 P2**：`KgTracingPerformanceTest`/`RecommendationKgFlowIntegrationTest` 部分用例 `assertThat(status).isIn(200, 403)`，权限配置回归时测试不报错。

属测试有效性问题，集成测试未跑通前难以验证修复效果，待 Docker Desktop 29 兼容问题解决后随集成测试一同治理。
